### 1.1 桌面 Win-Box

`D:/TVbox/Win-Box/data/user-config.json` 中的源条目：

```json

 "api":"file:///D:/TVbox/Win-Box/data/imports/py/85cda3fa-5efd-46c4-9034-8f7d5c176190/pikpak.py",

```

| 项 | 值 |
|---|---|
| 指向 | 绝对路径（不走 URL、不走仓库） |
| 文件 | 113,610 B / md5 `9c35d6e26a188644fbabe869306ca1c7` |
| 版本性质 | **桌面专用**：封面硬编码 `http://127.0.0.1:9978/img?u=…`，图片详情自动弹 Win-Box 内置画廊 |
| ext | 带 `proxy:7890`（桌面常驻代理，不会碰地区限制） |
| 更新方式 | 覆盖该路径的 `pikpak.py` → 重启 Win-Box |

### 1.2 手机（MisaTV / WinBox APK）

订阅 JSON `智能接口（引导）-含PikPak.json` 中的条目：

```json
{"key":"pikpak_mobile","name":"PikPak","type":3,
 "api":"file://Download/pikpak.py","ext":"{}"}
```

| 项 | 值 |
|---|---|
| 指向 | 手机存储的 `Download/pikpak.py`（相对路径） |
| ext | **空** `{}` → 完全靠源内 `_auto_proxy` / `_probe_proxy` 自动探代理 |
| 实际生效 | 用户 Download 里那一份，**优先于 APK 内置 assets** |
| 换 APK 会不会变 | **不会**。这是「只装 APK、图片行为不变」的根本原因 |

> 这一条值得你在自己机器上复核：如果 MisaTV 的 py 加载顺序是「assets 优先、Download 兜底」，
> 我这边的结论就反了 —— 用户替换文件后看不到变化，会很难查。

## 3. 本轮新发现：图片线路写死 40 张

### 3.1 证据

```python
# Muse 00:37 底座（也在你最初那份 121,169 B 的文件里）
imgs = [f for f in files if _is_image(f)]
imgs.sort(key=lambda x: _natural_key(str(x.get('name') or '')))
imgs = imgs[:40]          # ← 这里
```

`grep -c "imgs\[:40\]"` 在以下三份里都是 **1 处**：你最初那份 121,169 B 文件、00:37 底座、
我以 00:37 为底做的图集版。所以它来自你的实现血统，不是我这轮引入的。

### 3.2 影响

用户的图集目录普遍 110~130 张（见第 4 节实测）。**第 41 张之后在界面上完全不可达**：
线路只有 40 集，画廊只能翻 40 页。

### 3.3 修复

```python
imgs = imgs[:self.max_files]     # 默认 300，可由 ext.max_files 调
```

真实分享跑 `_share_image_detail()`，数「图片」线路集数：

| 分享 | 末层项数 | 目录内图片数 | 改前 | 改后 |
|---|---|---|---|---|
| `VOuCvo1P…` | 300 | 131 | 40 | **131** |
| `VOpS4nId…` | 300 | 124 | 40 | **124** |
| `VP3BgtoY…` | 300 | 116 | 40 | **116** |

抽查首集与末集缩略图，匿名 `GET` 均 `200 image/jpeg`（97,817 B / 149,520 B），
无 UA、无 Referer、无鉴权。

上限用 `self.max_files` 而非写死数字，是因为列表本身已被它钳住
（`_share_files` 里 `len(out) >= self.max_files` 就 break），**不会多花一次列表请求**。

## 4. 顺带跑出的两条实测数据

### 4.1 单链下钻是刚需，不是优化

拿用户本机 18 条真实解析记录逐条下钻，统计进入层数：

| 下钻层数 | 记录数 |
|---|---|
| 1 层 | 16 |
| 2 层 | 1 |
| 0 层 | 1 |

**17/18 条记录在根目录只有一个文件夹**。不下钻的话，用户点开每一条都只看到一个文件夹，
看不到任何内容。你 00:37 那份有下钻（范围限于 `if not fid:`），所以用户侧正常；
差异只在「从历史点开会不会重钻」。

### 4.2 `max_files = 300` 会截断大目录

同批 18 条里有 **5 条**末层正好取到 300 项：

| 分享 | 末层项数 | 图片 | 视频 | 目录 |
|---|---|---|---|---|
| `VP3BgtoY…` | 300 | 116 | 142 | 42 |
| `VOpS4nId…` | 300 | 124 | 176 | 0 |
| `VP3q7SUY…` | 300 | 0 | 0 | 300 |
| `VOuCvo1P…` | 300 | 131 | 167 | 2 |
| `VP5rYawq…` | 300 | 1 | 299 | 0 |

第 5 条最典型：1 张图 + 299 个视频 = 300，正好卡死，后面还有多少不知道。
本轮不改它，但**连播集数与图集张数都会受它影响**，所以图集上限跟着 `max_files` 走，
改一个数两边一起变。
